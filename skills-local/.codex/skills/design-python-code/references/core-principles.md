# 共通原則

## 判断の順序

1. 利用者と目的を確認する。
2. 局所化したい変更・障害を確認する。
3. 意味、状態、不変条件、権限のownerを確認する。
4. consumerへ提供する操作と契約を確認する。
5. DB、HTTP、SDK、framework等の実装詳細を分離する必要を確認する。
6. 最小案を実際の変更シナリオで検証する。

packageやpatternを先に決めない。`Clean Architecture`、`DDD`、`feature-first`、`hexagonal`等の名前は、上記の必要性を満たす場合にだけ実現手段として使う。

## 凝集と責務

- 同じ意味、不変条件、状態変更権限を持つものを近くへ置く。
- 同じ時期に変わるという理由だけでなく、誰が変更理由を所有するかを見る。
- SRPを「1 file 1 class」や短いfileと同一視しない。一つのmoduleが一つの理解可能な責務を持つかで判断する。
- file数やdirectory階層の少なさを、それ自体で単純さの証拠にしない。
- 逆に、分類のためだけのdirectoryを増やさない。navigateする負担もcostとして扱う。

## OCPと抽象化

OCPを「既存fileを変更してはいけない」と解釈しない。既存の業務ルール自体が変わるなら、そのownerを変更する。

抽象化は次のいずれかが確認できる場合に検討する。

- 複数実装が現在存在する。
- 具体的な追加予定または交換シナリオがある。
- 外部技術の型・例外・lifecycleをconsumerから隔離する。
- failureやtest doubleを契約として扱う必要がある。
- callerに散る分岐を一つのvariation pointへ閉じ込める。

「いつか必要かもしれない」だけでProtocol、base class、Factory、Strategy、Registryを追加しない。

## 証拠の扱い

- 確認済み: code、設定、test、実データ、userの明示情報から確認できる。
- 仮定: 作業を進めるために置いた前提。設計を左右するものは明記する。
- 提案: 未実装の将来状態。現状の事実と混ぜない。
- 未確認: 調査できず、判断に影響しうる事項。ownerまたは確認方法を示す。

既存の業務用語とmodule名を優先し、一般論から新しいcategoryを作らない。
