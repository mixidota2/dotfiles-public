# 在庫集計libraryのpackage化案：設計レビュー

## 結論

**`stock/__init__.py`のre-exportで既存の公開入口を保つ方針と、`queries.py` / `commands.py`への責務分割は、別々に評価すべきです。** 前者は`from stock import reserve`を維持する手段になります。後者について「参照の変更はqueriesだけ、予約の変更はcommandsだけに閉じる」とは、今の情報からは言えません。

現時点では、二分案を検証済みとして承認せず、まず現状維持を比較対象に残すのが妥当です。package化が別の理由で必要なら、**両関数を同じ`inventory.py`に残し、公開入口だけ整える最小案**を暫定候補にできます。これも保存・競合・公開契約を確認する前の設計候補であり、移行の安全性を保証したものではありません。

実装・repository調査・test実行は行っていません。以下は依頼文を根拠にした設計レビューです。実コードの欠陥を発見したという報告ではありません。

## 1. 先に修正・確認したい点

### 重要：操作の分類だけでは、変更理由は分離されない

- 根拠：提示案は`available_qty`を参照側、`reserve`を予約側へ分け、変更が各fileに閉じると説明しています。
- 反例：仮に「利用可能数」の定義へ安全在庫を織り込む変更があり、予約可否もその定義に従うなら、両方に影響します。二つのfileで同じ計算や判断を独立して持てば、変更漏れが起きます。
- 最小の修正方針：説明を「操作の入口は分かれる。共有する在庫の意味・不変条件の変更は、そのownerへ集約する」に改める。共有ownerを新しいclassやmoduleにするかは、実際の処理を見て決めます。
- 残る確認：両関数が本当に同じ在庫概念を扱うか、既に共通の判断箇所があるかは未確認です。両fileが同時に変わること自体を欠陥とはしません。

### 重要：予約の安全性を、file境界では説明できない

- 根拠：保存先、正となる在庫source、同時予約を制御する主体が未確認です。
- リスク：もし「残数を読む→予約可能と判断→書く」を別々に実行しているなら、間に別の予約が入り得ます。参照と更新が同じDBでも、それだけでは安全性の証明になりません。
- 最小の修正方針：予約可否の最終判断と状態変更を誰が一貫して確定するのかを特定します。仮に過剰予約を禁止するなら、競合下でもそれを守る仕組みを、その確定権限のある場所で保証する必要があります。具体的なtransaction、条件付き更新、外部service等の選択は未決定です。
- 残る確認：`available_qty`は確定判断用か、表示用のsnapshotか。後者なら、表示した数量と予約時の結果が異なる場合の契約が必要です。別sourceを使う設計も、それ自体では不適切とは言えません。

### 要確認：re-exportが守るのは、まず名前の入口

- 根拠：確認できている外部consumerの利用方法は`from stock import reserve`です。
- リスク：このimportが通っても、引数、戻り値、例外、side effect、retry時の結果まで互換とは限りません。また`__init__.py`から両moduleを通常のimportで読み込めば、一方しか使わないconsumerにも他方の初期化や依存が到達し得ます。
- 最小の修正方針：既存の公開契約を記録し、公開入口から実際の依存・初期化まで確認します。facadeに業務判断や新しい接続初期化を足さない方針にします。
- 残る確認：現在`stock`と`inventory.py`がどう接続されているか、他の公開importやcallerがあるか。`available_qty`が公開APIかどうかも不明なので、新規公開を前提にしません。

## 3. 比較する構成と、暫定案

### 現状維持

分かっている配置はここまでです。親directoryや現在の公開経路を補って「現行tree」とはしません。

```text
位置未確認の inventory.py
  available_qty
  reserve

外部から使われる入口: stock.reserve
入口と inventory.py の接続: 未確認
```

二つの操作が同じ在庫の意味・状態を扱い、現在のmoduleが理解できる大きさなら、同居は自然です。file数を増やす必要性は、依頼文からは確認できません。

### package化が必要な場合の最小候補B

```text
stock/
  __init__.py
  inventory.py
```

- `stock`：在庫操作の公開名前空間。別service、独立した状態authority、別release単位を新設する意味ではありません。
- `__init__.py`：確認済みの`reserve`と、調査で既存公開APIと確認したsymbolを公開します。在庫計算、予約判断、retry、保存、独自のmutable stateを持たせません。
- `inventory.py`：二つの操作と、実際に共有する在庫の意味・判断を近くに置く候補です。永続状態をこのmoduleのglobal変数に移す提案ではありません。既存の保存・設定注入方法は確認して引き継ぎます。
- 公開面：`from stock import reserve`を維持する方針です。consumerへ`stock.inventory`への移行を要求しません。ただし既存の内部path利用の有無は確認します。
- 非目的：新しい`Protocol`、`Repository`、`Service`、DI用module、例外階層を、このレビューだけで追加しません。

この候補は、共有する意味や状態の所有を調べる間に、操作分類による境界を増やさないための比較案です。既存構成が既に同じ目的を満たしていれば、移動自体を見送れます。

### 元の二分案Aが妥当になり得る条件

```text
stock/
  __init__.py
  queries.py
  commands.py
```

参照固有の集計・出力処理と予約固有の更新処理が、それぞれ独立して説明でき、実際の変更履歴やtestから別の変更理由を持つと確認できるなら候補になります。その場合も、共有する業務判断、状態authority、source、失敗時の責任が一意に辿れる必要があります。

- `queries.py`：参照固有の読取・集計・結果変換。予約の最終可否を、古い読取結果だけで保証しない。
- `commands.py`：予約要求を受けて確定主体へ至る操作。表示・集計専用処理を引き取らない。実際の書込み権限がどこにあるかを明示する。
- 利点：独立性が実在すれば、操作別に理解・testしやすくなる。
- cost：共有ルールの二重化、cross-import、初期化依存、複数fileを追う負担が増える可能性がある。
- 再検討条件：一つの在庫ルール変更で両fileの同じ判断を修正するなら、共有判断のownerを見直す。単に`common.py`へ逃がすことは解決としない。

## 5. 依存と実行経路の追跡

矢印の種類を分けます。どちらの候補でも、確認できるのは公開入口までです。

- **現状のimport依存**：外部consumer → `stock` → `reserve`の提供元〔接続・推移的依存は未確認〕。
- **候補Bのimport依存**：外部consumer → `stock/__init__.py` → `stock/inventory.py` → 既存の依存先〔未確認〕。
- **候補Aのimport依存**：外部consumer → `stock/__init__.py` → `commands.py` / `queries.py` → 下流依存〔未確認〕。両方を通常のre-exportで読み込む構成なら、予約だけをimportしても参照側の依存が読み込まれ得ます。
- **予約のruntime経路**：consumer → `reserve` → 入力検証・判断〔所在未確認〕→ 実際に選択される実装〔設定・DIとも未確認〕→ 確定・保存〔有無・場所未確認〕→ 結果または例外 → consumerのretry判断〔未確認〕。
- **参照のruntime経路**：caller〔未確認〕→ `available_qty` → 読取source・集計〔未確認〕→ 結果。公開入口を通るかも未確認です。
- **他の入口**：CLI、job、管理操作、maintenance script等は、存在も未確認です。見つかった経路ごとに同じtraceを取り、予約や直接書込みを迂回していないか調べます。新しい入口の存在は仮定しません。

追う対象は直接importだけではありません。入力・戻り値の具体型、外部例外、接続や設定の初期化が公開入口まで漏れていないかも確認します。共有mutable stateを移す場合は、同じ名前でも別instanceを持つ経路が生じないかを確認対象にします。

内部実装から公開facadeへ逆importさせる必要は通常ありません。組立ては既存方式を確認して再利用します。依存逆転が必要かは、外部型・失敗契約の漏出や交換/test上の必要性から決め、矢印を整えるだけの`Protocol`は導入しません。

## 8. 次に確認すること：判断が変わる順

依頼時点で追加情報がないことは承知しているので、回答を待つ前提にはしません。次にrepositoryや担当者へアクセスできる際、以下の順に確認すると判断が進みます。

1. **予約1件と参照1件の具体的な経路。** `reserve`と`available_qty`の本体、呼び出す実装、設定・DI、保存先を追う。「何を正とし、誰が最終確定するか」を一枚に記録する。関数名やfile名だけでは判定しない。
2. **競合・再試行の契約。** 同じ在庫への同時要求、同一要求の再実行、保存後の応答喪失について、期待結果と責任主体を確認する。関連test・保存先の制約・外部serviceの契約を根拠にする。過剰予約防止と重複実行防止は分けて確認する。
3. **公開入口と迂回経路。** `stock`の現在のexport、全caller、実行入口、直接書込み経路を検索し、既存APIの入力・結果・例外・side effectを記録する。docs、test、配布設定、repositoryの作業規約もこの時点で読む。
4. **分割する理由。** 最近の代表的な変更やtestを少数見る。参照専用・予約専用の変更が本当に独立するか、共通の在庫ルールを二重に編集していないかを調べる。package化だけで得たいものも確認する。

判定の分かれ目は明確です。独立した変更理由と所有関係が確認できれば二分を進められます。同じ意味・状態を一体で扱い、分割による隔離効果がなければ同居を保ちます。別sourceを使うなら整合性・鮮度の契約を明示します。いずれでも既存の公開入口を維持する価値は残ります。

実装へ進む場合の検証は、公開importとAPI互換test、共有ルールのtest、確認された競合・retry契約のtest、必要な保存先integration test、import・初期化依存の確認、repository既定のlint/type checkです。現時点ではすべて未実行であり、実装・検証完了は主張しません。
