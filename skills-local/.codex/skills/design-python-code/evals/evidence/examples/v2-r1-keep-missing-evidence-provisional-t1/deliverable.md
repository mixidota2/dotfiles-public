# 在庫集計 library の package 化案：設計レビュー

## 結論

**`from stock import reserve` を維持する方針は妥当です。一方、`queries.py` / `commands.py` への二分と「変更がそれぞれだけに閉じる」という説明は、現時点では採用を確定できません。** 公開 import の安定化と、内部の責務分割は別の判断です。

まず現状維持を比較対象にし、package 化が必要なら、両関数を同じ実装 module に残して公開窓口から公開する最小案を暫定候補にします。状態・呼出し経路の確認後に分割の要否を決めれば十分です。以下は設計案への指摘であり、実装上の不具合を確認したものではありません。

### 重要な指摘

1. **変更局所性の説明が強すぎます。**
   - 根拠：依頼文では二つの関数名と移動先だけが分かり、共有する在庫定義・状態・依存は不明です。
   - 反例：予約可能数の業務上の定義を変える場合、その定義を表示する処理と予約を許可する処理の両方が影響を受ける可能性があります。これは必要な同時変更であり、単にファイルを分けても消えません。両処理が同じ判断を独立実装すると、むしろ不一致の危険があります。
   - 最小修正：「独立した参照処理の変更は queries、独立した予約手順の変更は commands を主対象にする。共有する意味・整合性契約の変更は、その所有箇所と関連処理を確認する」と説明を限定します。実際に共有しているかは未確認です。

2. **予約の正しさを担う境界が、提案からは分かりません。**
   - 根拠：保存先、在庫 source、同時予約の制御、例外・retry 契約が未確認と明示されています。
   - 影響：仮に過剰予約を防ぐ要件があるなら、在庫を読んでから別操作で書くだけでは、並行実行時の安全性を説明できません。更新成功後に応答だけ失われる場合も、無条件 retry が安全とは限りません。
   - 最小修正：意味を定める場所、更新可否を決める場所、実際の書込み経路、正として保存する source を区別して確認します。DB transaction、条件付き更新、外部サービス等のどれを使うかは、保存方式と既存保証が分かるまで決めません。

3. **re-export は互換性を守る手段ですが、それだけでは互換性の証明になりません。**
   - 維持が必要と確認できるのは `from stock import reserve` です。引数、戻り値、例外、副作用、初期化も含む契約は未確認です。
   - `inventory.py` と現在の `stock` の位置関係が不明です。既存の公開処理・設定を持つ `__init__.py` がある可能性もあるため、上書き前提にはできません。
   - 両 module を通常の import で re-export する場合、片方だけを使う consumer にも他方の推移的依存や import 時初期化が届き得ます。分割だけで依存を隔離したとは言えません。

## 事実と判断範囲

- 確認済み：`inventory.py` に `available_qty` と `reserve` がある。外部 consumer は `from stock import reserve` を使う。提案は queries / commands への分割と `stock/__init__.py` での re-export。
- 利用者と目的：外部 consumer の呼出しを保ち、保守担当者が変更の影響を追いやすくする。後者は提案の説明から読み取れる目的で、追加の機能要件ではありません。
- 未確認：実コード、現行 tree、他の公開 symbol / caller / entrypoint、設定・DI、test、状態・不変条件・保存・障害契約。
- 制約：repository は未提供。コード行番号や実 import graph は示せず、実装・実行検証は行いません。参照と予約が同じ source を使うことも、参照値が常に最新であることも仮定しません。

## 最小案との比較と暫定構成

- **A：現状維持。** 既存の `stock` 公開窓口が目的を満たし、実装の理解・変更に問題がなければ再編不要です。二つの関数があるだけでは分割理由になりません。
- **B：公開窓口＋単一実装。** package 化に具体的な必要がある場合の暫定候補です。既存の構成に応じて移動自体が不要な可能性もあります。
- **C：queries / commands に分割。** 読取りと更新で独立した責務・依存・変更履歴が確認できれば候補になります。共有ルールや整合性の所有者を分裂させないことが条件です。CQRS や別 read model の導入まで承認する案ではありません。

B の概念的な tree（現行 tree の再現ではありません。配置 prefix は未指定）：

```text
stock/
├── __init__.py       # 既存の公開 import を維持
└── inventory.py      # available_qty と reserve の既存実装を維持
```

- `stock`：在庫操作の公開名前空間。新たな独立システムや別の状態所有者を作りません。
- `__init__.py`：公開 symbol を結び付ける窓口。予約判断・在庫状態・retry を持たせません。`reserve` の公開を維持し、その他は既存の公開契約を確認して保ちます。`available_qty` を新規に公開することまでは決めません。
- `inventory.py`：両操作の実装を当面まとめて保持。保存責任や不変条件をここへ新しく移す提案ではありません。それらの現在の所有者は未確認です。
- 設定・DI：既存方式を確認して維持します。新しい Protocol、repository 抽象、model、composition root は根拠不足のため追加しません。
- 得るもの：内部配置変更から既存 consumer を守りつつ、確認前の分断を避けられること。
- 費用・再検討条件：公開窓口の維持と import 確認が必要。読取りと更新が実際に独立して大きく変わるなら、単一 module より C が読みやすい可能性があります。

## 境界と依存の確認

### Merge / Delete

境界の削除は関数・機能の削除とは区別します。

| 対象 | Merge：統合すると失うもの | Delete：境界をなくすと失うもの／判断 |
| --- | --- | --- |
| `stock` package 境界 | 単一の `stock` module でも同じ公開 import を提供できる可能性がある。package 固有の必要性は未確認。 | 公開名 `stock.reserve` 相当の窓口を代替なしに消すと既存 consumer を壊す。必要なのは公開契約で、package 形式自体が必須とは未証明。 |
| `__init__.py` の公開窓口 | 実装と統合しても import は維持し得るが、公開面と実装移動の分離は減る。現行配置と比較が必要。 | package 案で re-export を取り去れば、代替なしには既存 import を維持できない。互換性を理由に公開窓口を保つ。 |
| `queries.py` と `commands.py` | 両者を既存の `inventory.py` に戻して失う独立性は、現時点では実証されていない。 | 分類の境界だけを取り去っても、二つの関数と公開 API は残せる。今は二分を必須にしない。 |
| 暫定 B の `inventory.py` | 実装を公開窓口に統合できるが、既存実装を保持する利点と比較する必要がある。 | 関数を残して境界を消すことは可能。既存の実装置場を維持する暫定措置であり、検証済みの最終境界とはしない。 |

名称を伏せても説明できる責務は「利用者へ安定した操作を提供する」「数量を求める」「予約を実行する」です。後二者が独立した状態・判断を所有するかは、名前からは決まりません。

### Entry-point trace

既知の入口は外部 consumer の `from stock import reserve` のみです。

- 現行の import：consumer → `stock` → **`inventory.reserve` への結び付きは未確認**。
- C の提案上の import：consumer → `stock.__init__` → `commands.reserve`。同じ初期化内で queries も import するなら、その依存も推移的に到達します。
- B の提案上の import：consumer → `stock.__init__` → `inventory.reserve`。
- 実行時の call / 状態の経路：consumer → 公開された `reserve` → 判定・更新処理 → 保存先／結果。判定と書込みの所有者、設定・DI で選ばれる実装、failure と retry の責任はすべて未確認です。re-export は名前の束縛であり、追加の runtime 転送関数を必須にするものではありません。
- 下流から運ばれる型・例外・SDK 初期化の有無も未確認。他の entrypoint は存在も未確認で、ここで網羅済みとはしません。

暫定案では実装から公開窓口への逆 import を増やさない方向とします。ただし実 graph は未検証です。依存逆転のためだけの Protocol は作りません。provider の交換予定は示されていないため、架空の複数実装も置きません。

## 次に確認すべきこと

優先順に、次の三組で判断を進められます。

1. **状態と安全性**：両関数の実装と、そこから辿る保存・読取り処理。数量の定義、同じ source か別 source か、許容する鮮度、予約可否の決定者、同時予約を防ぐ仕組み、他の writer を確認する。実装・保存先の制約・運用経路が確認先です。
2. **公開契約と全入口**：現在の `stock` の配置・公開処理、caller の import と呼出し、entrypoint、設定・DI、既存 test。引数・戻り値・公開例外と、`available_qty` の公開状況を確認する。これで facade の変更範囲と移行時の互換性が決まります。
3. **障害契約と分割の根拠**：予約の成功・拒否・結果不明、retry の実行者、重複時の扱いを API 文書・実装・障害 test で確認する。あわせて直近の参照変更と予約変更の例を各一件見て、共通判断や同時変更が実際にどこへ集まるかを確認する。

その後、必要な公開 import / consumer test、予約の状態保証と並行実行の test、必要に応じた障害注入・保存連携 test、推移的依存の確認を実施します。lint / type check 等は repository の既定方式に従います。**今回は実装も test 実行もしていません。現時点で進められる判断は、公開契約の維持を要件にし、二分の断定を弱め、状態所有者の確認前に構造を固定しないことです。**
